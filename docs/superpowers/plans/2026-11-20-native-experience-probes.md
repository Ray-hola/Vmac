# 三项验证

日期：2026-11-20　对应路线图的「顺序 0」

这三项是试验，产出是答案，不是要保留的代码。试验用的改动放在单独的分支 `probe/native-experience` 上，试完不合并。结论写回 [路线图](../specs/2026-11-20-vmac-native-experience-roadmap.md) 第 3、4 节和界面设计说明第 9 节。

试验版本的打包和安装沿用现有做法：在已安装的 VMac 基础上增量打包，安装前先通过 SSH 让客机关机，再退出 VMac。

## 验证 A：哪些设备妨碍保存状态

**问题**：给客机加上声音设备或共享目录以后，还能不能保存和恢复状态？

**做法**：苹果的虚拟化框架自带一个检查，可以直接回答某个配置能否保存状态，不需要真的保存一次。

- [ ] 在 `third_party/lima/pkg/driver/vz/vm_darwin.go` 的 `createVM` 里，`vmConfig.Validate()` 之后，对当前配置调用 `vmConfig.ValidateSaveRestoreSupport()`，把结果和错误文字写进日志，前缀用 `probe save-restore base:`。
- [ ] 另外组装三份只用于检查、不启动的配置，各调用一次并写日志：
  - 加一个带输出流的声音设备，前缀 `probe save-restore audio-out:`
  - 加一个带输出流和输入流的声音设备，前缀 `probe save-restore audio-in-out:`
  - 加一个 VirtioFS 共享目录（指向一个临时空文件夹，用 macOS 客机的自动挂载标签），前缀 `probe save-restore virtiofs:`
- [ ] 打包为试验版本，安装，启动客机。
- [ ] 读取 `~/.vmac/logs/events.jsonl` 里四条 `probe save-restore` 记录。

**判定**：每条记录是 `true`，或者 `false` 加框架给出的原因。

**后续**：如果 `base` 是 `true`，再做一次真实的保存和恢复，记录保存耗时、状态文件大小和恢复耗时。做法是在 `createVM` 之后检查状态文件是否存在，存在就调用 `RestoreMachineStateFromURL` 再 `Resume`，否则正常启动；保存由一个试验用的命令触发，先 `Pause` 再 `SaveMachineStateToPath`。如果 `base` 是 `false`，记录原因，判断是哪一个现有设备导致的。

## 验证 B：画面跟随窗口是否稳定

**问题**：打开自动调整以后，调整窗口大小和进出全屏时，客机会不会黑屏、卡住或者反复调整？

**做法**：

- [ ] 在 `internal/maclogin/bridge_darwin.m` 里把 `view.automaticallyReconfiguresDisplay` 改成 `YES`，和验证 A 的改动打进同一个试验版本。
- [ ] 启动客机并登录后，通过 SSH 在客机里每秒读取一次屏幕的点数和缩放倍数（用 JXA 读 `NSScreen.screens[0]` 的 `frame` 和 `backingScaleFactor`），有变化就记一行。
- [ ] 请用户做四个动作，每个动作之间停 5 秒：把窗口拖大；把窗口拖小；进入全屏；退出全屏。再点一次侧栏里的其他页面然后回到桌面。
- [ ] 对照记录：每个动作之后客机分辨率变化了几次，最终是否等于画面区域的大小。

**判定**：每个动作之后分辨率在 2 秒内稳定下来，变化不超过 2 次，客机没有黑屏或失去响应，切到其他页面再回来不触发调整。四条都满足算稳定。

## 验证 C：全屏后的切换手势

**问题**：全屏以后，四指左右轻扫和 `⌃←/→` 能不能在 Mac 和客机之间切换？

**做法**：现在安装的版本就能试，不需要改代码。

- [ ] 请用户在 VMac 的「窗口」菜单里点「进入全屏」。
- [ ] 请用户试：四指向右、向左轻扫；按 `⌃→`、`⌃←`；在客机里三指或四指上推，看调度中心是 Mac 的还是客机的。

**判定**：两种方式都能离开和回到客机所在的桌面空间，算可用。任何一种被客机截走，就记录下来，在界面第一期里处理。
